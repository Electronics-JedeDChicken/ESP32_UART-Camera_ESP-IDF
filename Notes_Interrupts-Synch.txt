*Tell CPU to pause what it's doing since something "more" important happened, after ISR then resume...

Btn Bounce- mech btn's don't produce clean transition (e.g. LOW->HIGH but actually HIGH->LOW->HIGH->LOW->HIGH w/in few ms thus 1 press may trigger multiple intr's)
*Due to noise/non-idealities...

    *Disable intr briefly & re-enable after debounce interval

Higher prio task- suppose you give gpio intr the lowest prio, this still means that it will be prioritized over normal tasks right?
*Intr prio & Task prio are separate (Intr prio > Task prio always)
If ISR wakes low-prio task then nothing changes (higher-prio task keeps on running)
*Low prio isn't ignored but its state changes to ready
*FreeRTOS task states- Running, Ready (can run, waiting for CPU), Blocked (waiting, queue/semaphore/delay), Suspended (explicitly)
*Intr states (not formal but mental model)- Disabled > Enabled(Waiting) > (Event occurs) > Pending > (CPU accepts it) > Running ISR > ISR finishes > Enabled(Waiting)

ISR- func that runs when intr occurs
*Not normal func- executed by interrupt controller
*Flash vs IRAM- see below...

Rule of Thumb- keep ISRs short (must finish w/in few micros, like flag/notif, musn't do entire job)
*We can just wake the task needed
*E.g. notif taks, give semaphore, send data to queue, set event bit, update small variable, exit quickly
    *Not- delay, allocate lots of mem, complicated operations

W/o RTOS (intr simply intr's CPI) vs W/ FreeRTOS (intr may need to wake task, thus we have ...FromISR() funcs)
*Rule of Thumb- don't call normal FreeRTOS APIs from ISR, normal APIs assume they're running inside task & ISR isn't task
    *What will happen- 
    *vTaskNotifyGiveFromISR()- wake 1task, no data, fastest, great replacement for binary semaphores
    *xQueueSendFromISR() instead of xQueueSend() (this is used for tasks not ISRs)- send data (to queue?), pass data bet. contexts, FIFO
    *xSemaphoreGiveFromISR()- signal smthng/event happened, carries no data, just synch, can be used by mutliple tasks
    *xEventGroupSetBitsFromISR()- set flags, 1obj many flags, for waiting for multiple indep events
    *vTaskDelay()- never
    *Notif vs Queue vs Semaphore, examples...-

Synchronization Primitives- 
*Binary Semaphore- to signal an event, ISR gives while Task takes, 0/1, no ownership, ISR-safe (GiveFromISR), e.g. btn press
*Counting Semaphore- like binary but counts multiple events, ISR gives 3x (e.g. UART receive 3 packets), resource pool w/ N identical resources
*Mutex- to protect shared resources, has ownership, prevents simultaneous access, supports prio inheritance
*Recursive Mutex- same task can lock multiple times, for nested func calls
    *The 2 mutex musn't be used in ISR
